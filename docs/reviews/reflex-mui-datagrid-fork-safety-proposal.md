# Proposal for `reflex-mui-datagrid`: fork safety and O(page) sorting

Audience: the `reflex-mui-datagrid` maintainer.
Status: proposal only — no changes have been made to the library.
From: `just-dna-lite` (currently pinned to 0.3.8), which hit the same production
wedge that motivated 0.3.10.

Full root-cause write-up with reproductions: `docs/GRANIAN_POLARS_FORK_DEADLOCK.md`.

## TL;DR

The 0.3.10 "Granian-safe sorting" fix stops the hang, but the diagnosis behind it is
wrong in a way that matters:

- The deadlock is caused by **`fork()` inheriting a warm Rayon pool**, not by which
  thread the sort runs on. It is a process-model bug, fixable in ~5 lines in the
  *application*, and there is nothing about Polars' sort that is unsafe on a request
  thread of a *spawned* worker.
- Of the three mitigations in that release, **only the Python `list.sort` does
  anything** — it never touches Rayon. The one-worker `ThreadPoolExecutor` is inert
  (Rayon's pool is process-global, so another thread of the same poisoned process is
  still poisoned), and `POLARS_MAX_THREADS=1` is inert too (measured below).
- That Python sort costs real scalability: it replaced an O(page) lazy query with a
  full `collect()` plus a Python-level sort of every row, on the request thread.

So the library is currently carrying an expensive workaround for a bug it cannot fix
and did not cause. The asks below are about the parts that *are* the library's to own.

## Evidence

Rayon's pool is created on the **first Polars operation**, not at import. A forked
child inherits its latches but none of its worker threads, so the first parallel op
parks forever with the GIL released — no traceback, SIGTERM ignored, SIGKILL only.

One interpreter, repeated forks:

| Sequence | Child `sort()` |
|---|---|
| `import polars` → `fork()` | ok |
| `import polars` → **one Polars op in the parent** → `fork()` | **hangs; needs SIGKILL** |
| `POLARS_MAX_THREADS=1` (also 4, 16) → Polars op in parent → `fork()` | **hangs** |
| `spawn` child instead of fork, warm parent pool | ok |

End-to-end, trivial ASGI app that sorts 200k rows in its handler, Granian
`workers=1`, Rayon warmed in the parent before `serve()`:

| start method | Result |
|---|---|
| `fork` | worker starts, logs `Started worker-1`, **HTTP never responds** |
| `spawn` | `sorted-ok` |

Reproduction scripts are at the end of this document.

## Ask 1 — document the real cause; don't make callers pay for it

The application-side fix is a start-method change:

```python
import multiprocessing
multiprocessing.set_start_method("spawn", force=True)   # before the server starts
```

(Spawned children re-import `__main__`, so the entry point must be
`__main__`-guarded or the worker dies with the `freeze_support()` RuntimeError.
Console scripts generated by uv/pip already are.)

Suggested: a short "Deployment / process model" section in the README stating that
any server which forks workers after the app is imported — `gunicorn --preload`,
Granian's `MPServer`, uvicorn under gunicorn — will deadlock on the first parallel
Polars call, and that `spawn` is the fix. That is more valuable to users than a
library-side workaround, because it fixes *all* their Polars code, not just the grid.

Also worth warning about explicitly: **`POLARS_MAX_THREADS=1` does not help.** Measured
at 1, 4 and 16 threads, the forked child hangs every time — even a single-worker pool
loses that worker to the fork. It reads like a mitigation, so users will try it and
believe they are covered.

## Ask 2 — retire the `ThreadPoolExecutor`, or say what it is for

If it is there for the deadlock, it does not help and can go. If it is there to keep
the event loop free, it does not achieve that either, because
`handle_lf_grid_sort` / `handle_lf_grid_filter` / `handle_lf_grid_scroll_end` are
**sync generators**: a Reflex generator handler holds the state lock for its entire
execution, and `yield` pushes deltas without releasing it. Every queued event —
tab clicks, other grids, unrelated buttons — waits for the sort either way.

## Ask 3 — make the grid handlers async background events

```python
@rx.event(background=True)
async def handle_lf_grid_sort(self, sort_model: list[dict[str, Any]]) -> None:
    async with self:                      # brief: publish "Sorting…"
        self.lf_grid_loading = True
        self.lf_grid_stats = "Sorting..."
    page = await self._compute_page(...)  # no state lock held
    async with self:                      # brief: publish results
        self.lf_grid_rows = page.rows
        self.lf_grid_loading = False
```

This is what actually keeps the UI responsive, and it composes with Ask 4.

## Ask 4 — materialize once, paginate cheap (replaces the Python sort)

`lf.sort(...).slice(offset, n).collect()` is O(rows) on **every** click. Polars does
not reduce it to a bounded top-k in general: `explain()` shows a dynamic-predicate
pushdown for single-key sorts only, while multi-key sorts materialize a full sort.
The 0.3.10 Python `list.sort` is O(rows) too, plus it materializes every row into
Python objects.

Instead, on a filter/sort-model change, stream the sorted+filtered frame to a temp
parquet once, then serve every page as a slice off that artifact:

```python
# once per (cache_id, filter_model, sort_model)
lf_sorted = apply_sort_model(apply_filter_model(cache.lf, filt, schema), sort, schema)
lf_sorted.sink_parquet(artifact)        # streaming, spills to disk, bounded RAM

# every page, including scroll-append
pl.scan_parquet(artifact).slice(offset, page_size).collect()
```

Measured on 2M rows:

| Step | Time |
|---|---|
| `scan_parquet(src).sort(k).sink_parquet(tmp)` | 0.1 s |
| `scan_parquet(tmp).slice(1_500_000, 100).collect()` | 3 ms |

Scroll-append becomes O(page) instead of re-sorting per chunk, which is a real win
over both 0.3.8 and 0.3.10. Needs an artifact cache keyed by
`(cache_id, filter_model, sort_model)` with an LRU bound and cleanup on eviction /
shutdown. Unsorted, unfiltered grids should keep scanning the source directly.

## Ask 5 (optional) — a pluggable page source

Consumers with heavier data may want pages produced somewhere other than the calling
process. A narrow seam would let them supply that without forking the library:

```python
class GridPageSource(Protocol):
    async def prepare(self, source) -> GridMeta: ...
    async def page(self, source, filter_model, sort_model, offset, limit) -> GridPage: ...
    async def value_options(self, source, field, max_unique) -> list[str]: ...
```

`LazyFrameGridMixin` would default to the in-process implementation, unchanged.
`just-dna-lite` would supply one backed by a `spawn`-context `ProcessPoolExecutor`,
which is how we are solving it locally (currently by overriding the handlers in a
local mixin — workable, but it duplicates library logic across four grid states and
will drift from upstream).

Two implementation notes if you take this up:

- **Passing the frame to another process:** `LazyFrame.serialize()` round-trips fine
  for `scan_parquet`-backed plans, but **fails for `polars_bio.scan_vcf`** with
  `ComputeError: python: ModuleNotFoundError: No module named 'cloudpickle'`, because
  polars-bio registers a Python IO source. A source *descriptor* (path + reader kind,
  reconstructed with `scan_file` in the worker) is more robust than serializing plans.
- **`polars_utils` imports `reflex`,** so a worker that needs `apply_filter_model` /
  `apply_sort_model` / `_dataframe_to_dicts` pays a reflex import. Splitting the pure
  Polars helpers into a reflex-free module would make out-of-process workers cheap.

## Reproduction scripts

Isolated:

```python
import os, time
import polars as pl

pl.DataFrame({"a": [3, 1, 2]}).lazy().sort("a").collect()   # warm Rayon; comment out -> no hang

pid = os.fork()
if pid == 0:
    pl.DataFrame({"a": list(range(300_000))[::-1]}).lazy().sort("a").slice(0, 3).collect()
    os._exit(0)                                              # never reached
deadline = time.time() + 6
while time.time() < deadline:
    if os.waitpid(pid, os.WNOHANG)[0]:
        print("child finished"); break
    time.sleep(0.1)
else:
    os.kill(pid, 9); print("child HUNG — SIGKILL required")
```

Under Granian — `tapp.py`:

```python
def app():
    async def _app(scope, receive, send):
        if scope["type"] != "http":
            return
        import polars as pl
        n = pl.DataFrame({"a": list(range(200_000))[::-1]}).lazy().sort("a").collect()["a"][0]
        await send({"type": "http.response.start", "status": 200,
                    "headers": [(b"content-type", b"text/plain")]})
        await send({"type": "http.response.body", "body": f"sorted-ok first={n}".encode()})
    return _app
```

`srv.py` — run with `METHOD=fork` (wedges) then `METHOD=spawn` (works):

```python
import multiprocessing, os, sys

def main():
    sys.path.insert(0, os.path.dirname(os.path.abspath(__file__)))
    multiprocessing.set_start_method(os.environ["METHOD"], force=True)
    import polars as pl
    pl.DataFrame({"a": [3, 1, 2]}).lazy().sort("a").collect()   # warm Rayon in the parent
    from granian.constants import Interfaces
    from granian.server import Server
    Server(target="tapp:app", factory=True, address="127.0.0.1", port=8700,
           interface=Interfaces.ASGI, workers=1).serve()

if __name__ == "__main__":     # required for spawn
    main()
```

```bash
METHOD=fork  python srv.py &   # curl http://127.0.0.1:8700/  -> hangs forever
METHOD=spawn python srv.py &   # curl http://127.0.0.1:8700/  -> sorted-ok first=0
```

Versions used: polars 1.43.1, granian 2.7.9, reflex 0.9.6.post1,
reflex-mui-datagrid 0.3.8, Python 3.13, Linux.
