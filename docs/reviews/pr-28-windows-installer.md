# Review — PR #28: Windows installer & cross-platform CLI

**Author:** sebastianm-ionita · **Branch:** `sebastianm-ionita/win-installer` · **Base:** `main`
**Reviewer notes for a junior dev — read the whole thing before touching anything.**

First off: nice work. This PR does the hard, unglamorous part of cross-platform support
correctly. The Windows/Unix split in `_kill_process_group` and `_kill_port_owner` is clean,
moving off `os.execvp` to `subprocess.run` is exactly the right instinct (execvp replaces the

There's **one thing that must change before this merges**, one **bug**, and a few **nits**. None
of it is a knock on you — the big one is a thing almost everybody does once, and the point of this
doc is that you learn *why* and fix it *yourself*, because that's the part that sticks.

## 1. Blocking: the 51 MB `uv.exe` in the commit

You committed two binaries:

```
windows/uv.exe    51,935,232 bytes  (~52 MB)
windows/icon.ico     117,850 bytes  (generated by generate_icon.py)
```

**Why this is different from shipping a binary in the installer.** Shipping `uv.exe` *inside the
installer* is correct and intended — the end user needs it. Committing it *into git* is a different
thing. Git history is append-only and permanent: every person who ever clones this repo downloads
that 52 MB, forever, even after you "delete" the file in a later commit — because the blob still
lives in history. You can't take it back with a normal commit. The only ways to truly remove it are
rewriting history (what we'll do below, while it's still cheap) or a repo-wide `filter-repo`
surgery later (painful, breaks everyone's clones).

**Why it's also redundant.** Look at `.github/workflows/release.yml` — the release build already
does this for you:

```yaml
env:
  UV_VERSION: "0.7.8"
...
- name: Download uv for Windows      # release.yml:38
  run: |
    $uvUrl = "https://github.com/astral-sh/uv/releases/download/${{ env.UV_VERSION }}/uv-x86_64-pc-windows-msvc.zip"
    Invoke-WebRequest -Uri $uvUrl -OutFile uv.zip
    ...
    Copy-Item $uvExe.FullName windows/uv.exe
- name: Generate icon                 # release.yml:48
  run: windows/uv.exe run --with Pillow python windows/generate_icon.py
```

So in the real release path, CI downloads a **pinned, known** `uv 0.7.8` and regenerates the icon —
your committed copies get overwritten and never used. On top of the size problem, a binary blob in
the tree is *opaque*: a reviewer can't tell what version or build it is, and it will silently drift
from the `0.7.8` that CI ships. For something that runs on users' machines, "a `.exe` of unknown
provenance in the repo" is a smell worth taking seriously.

`icon.ico` is the same story — it's generated by `windows/generate_icon.py`, so there's no reason to
track the output.

### Fix it yourself — strip both from your branch

Good news: I checked, and both files were added **only in your tip commit** (the parent is `main`,
which never had them). That means a simple `--amend` removes them from history entirely — no
`filter-repo`, no drama. Here's the whole thing.

> These are *your* commands to run — I'm intentionally not doing this for you. Rewriting a branch is
> a normal skill and you should get comfortable with it. Read each step before running it.

```bash
# 0. Make sure your working tree is clean and you're on your branch.
git status
git switch sebastianm-ionita/win-installer

# 1. (Recommended) rebase onto the latest main first, so your branch is one clean commit on top.
git fetch origin
git rebase origin/main

# 2. Untrack the two binaries WITHOUT deleting them from disk (you still need uv.exe to build
#    the installer locally). --cached removes them from git's index only.
git rm --cached windows/uv.exe windows/icon.ico

# 3. Tell git to never track them again.
printf '\n# Build-time artifacts, fetched/generated by CI or the local build script\nwindows/uv.exe\nwindows/icon.ico\n' >> .gitignore
git add .gitignore

# 4. (After you add the downloader from section 2 below, also `git add windows/fetch-uv.ps1` here.)

# 5. Fold all of this into your existing single commit — no new "remove binary" commit needed.
git commit --amend
#    Leave the message as-is, or tidy it. Save and close the editor.

# 6. Confirm the blob is gone from your branch's history:
git cat-file -e HEAD:windows/uv.exe && echo "STILL THERE — stop and re-check" || echo "gone ✔"
git rev-list --objects HEAD | grep -i "windows/uv.exe" && echo "STILL THERE" || echo "gone ✔"

# 7. Publish the rewritten branch. Because you rewrote history, a normal push is rejected;
#    you must force. Use --force-with-lease, NOT --force (see the etiquette note below).
git push --force-with-lease
```

**Force-push etiquette** (worth internalising early):

- `--force-with-lease` refuses to push if someone else pushed to the branch since you last fetched.
  Plain `--force` blindly overwrites and can eat a teammate's work. Make `--force-with-lease` your
  default reflex.
- Force-pushing a **personal PR branch** that only you work on is completely normal and expected —
  this is what rewriting a PR looks like. Force-pushing a **shared/long-lived** branch (`main`,
  `develop`) is not; don't.
- One honest caveat so you're not surprised: after the force-push, GitHub may still hold the old
  52 MB blob server-side as an unreachable object for a while (their GC, not yours). That's fine —
  it's no longer part of your branch or the PR diff, which is what a reviewer and every future
  cloner see. The point of doing this *now* is that it never lands on `main` in the first place.

## 2. The proper fix: fetch `uv` at build time, don't store it

Removing the blob leaves a gap: how does someone building the installer **locally** (running
`ISCC.exe` on their own Windows box, outside CI) get `uv.exe`? The answer is the same thing CI does —
fetch it — but pulled out into a script both CI and humans can call. This is the "downloader / hook"
part of the fix.

Add `windows/fetch-uv.ps1`:

```powershell
# windows/fetch-uv.ps1
# Downloads the pinned uv.exe next to this script, for building the installer locally.
# CI does the same thing (see .github/workflows/release.yml) — keep the version in sync.
param(
    [string]$UvVersion = "0.7.8"   # keep in lockstep with UV_VERSION in release.yml
)
$ErrorActionPreference = "Stop"

$here = Split-Path -Parent $MyInvocation.MyCommand.Path
$dest = Join-Path $here "uv.exe"

if (Test-Path $dest) {
    Write-Host "uv.exe already present at $dest — skipping download."
    exit 0
}

$url = "https://github.com/astral-sh/uv/releases/download/$UvVersion/uv-x86_64-pc-windows-msvc.zip"
$tmp = New-Item -ItemType Directory -Path (Join-Path $env:TEMP ("uv-fetch-" + [guid]::NewGuid()))
try {
    Invoke-WebRequest -Uri $url -OutFile (Join-Path $tmp "uv.zip")
    Expand-Archive -Path (Join-Path $tmp "uv.zip") -DestinationPath $tmp -Force
    $uv = Get-ChildItem -Path $tmp -Recurse -Filter "uv.exe" | Select-Object -First 1
    if (-not $uv) { throw "uv.exe not found in downloaded archive" }
    Copy-Item $uv.FullName $dest
    Write-Host "Downloaded uv $UvVersion -> $dest"
} finally {
    Remove-Item -Recurse -Force $tmp -ErrorAction SilentlyContinue
}
```

Then document the local build as: `pwsh windows/fetch-uv.ps1` → `pwsh windows/uv.exe run --with
Pillow python windows/generate_icon.py` → run `ISCC.exe`. A couple of lines in the `windows/`
area (or a short `windows/BUILD.md`) is enough.

**Two design points I want you to notice — these are the actual senior-vs-junior distinctions:**

1. **One source of truth for the version.** Right now the pin (`0.7.8`) lives in `release.yml`. If
   you add `-UvVersion "0.7.8"` as a default in the script too, you now have the pin in *two*
   places, and they *will* drift. The cleaner move: have CI call your script
   (`pwsh windows/fetch-uv.ps1 -UvVersion $env:UV_VERSION`) instead of inlining its own download.
   Then CI and local builds run the *same code path* and there's exactly one place the download
   logic lives. That's the "hook" idea done right — don't duplicate, delegate.

2. **Don't reach for the easy-but-wrong version.** A tempting shortcut is to make the `.bat` download
   uv on first launch. Don't — the installer must ship `uv.exe` already bundled (that's what
   `installer.iss` copies into `{app}`), and end users may be offline-ish or behind proxies on first
   run. Fetching belongs at **build** time, not **launch** time. Keep the boundary clear.

This is optional-for-this-PR only in the sense that section 1 (removing the blob) is the hard
requirement; but the PR isn't really "done" until a local builder can get `uv.exe` without you
handing them a file. Land the downloader in the same PR.

## 3. Bug: `start_dagster` runs Dagster in the wrong directory

`src/just_dna_lite/cli.py:298` (the standalone `dagster` / `uv run dagster-ui` command):

```python
result = subprocess.run(
    [dg_cmd, "dev", "-f", str(dagster_file), ...],
    cwd=str(dagster_file.parent),   # <-- this
)
```

`dagster_file.parent` is `just-dna-pipelines/src/just_dna_pipelines/annotation/`. Compare with the
`start` command a few lines down (`cli.py:444`), which correctly uses `cwd=str(root)`. The old code
used `os.execvp`, which *doesn't change the directory* — so it inherited the user's cwd (the
workspace root). Your change quietly moved it.

Why it bites: `definitions.py:165` resolves a **cwd-relative** path:

```python
modules_dir = Path("data") / "modules"
```

With cwd pointing at the `annotation/` folder, that becomes `.../annotation/data/modules`, which
doesn't exist — so custom-module discovery silently loads nothing. (Most other paths survive because
they go through `get_workspace_root()`, which walks up to find the workspace `pyproject.toml`; but
bare relative paths like this one don't.)

**Fix:** make it match `start_all` — use `cwd=str(root)`. You'll need `root` in scope here (it's
already computed at the top of the function as the workspace root). One-line change.

*Lesson worth banking:* when you have two code paths doing "the same thing" (`start_dagster` and
`start_all` both launch `dg dev`), differences between them are usually bugs, not intent. When you
touch one, diff it against the other.

was "notice the download already exists in CI and make one code path serve both CI and humans."
Spotting duplication and collapsing it is most of what senior review actually is.
